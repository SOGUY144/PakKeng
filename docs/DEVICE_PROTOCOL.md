# DEVICE_PROTOCOL — ข้อมูลจาก ESP32 ถึงเว็บ

สถานะ: **ต้นแบบ ยังไม่ได้ทดสอบกับฮาร์ดแวร์จริง** เว็บรองรับรูปแบบนี้แล้ว
(`src/signal/WebSocketSignalSource.ts`) และมีโหมดสาธิตที่จำลองทุกช่องข้อมูล (`src/signal/MockSignalSource.ts`)
เฟิร์มแวร์ที่ส่งตามรูปแบบนี้อยู่ที่ [`firmware/`](../firmware/README.md) (compile ผ่านกับ esp32 core 3.3.12, การคำนวณมีเทสต์บนคอม, ยังไม่ได้ลงบอร์ดจริง)

## โครงสร้างที่ทำให้ต่ออุปกรณ์ภายหลังได้
```
ESP32 (ไมค์ INMP441 สองตัว) ──WebSocket──► SignalSource (mock | websocket)
   ──► SignalProcessor + quality.ts (สดหรือค้าง, ช่องไมค์หาย, ล้น, ระดับเสียง)
   ──► ตรรกะเกม (src/logic/*, เช่น call.ts: ตรวจพบการลองพูด / คุณภาพสัญญาณ / สรุปรายคำ)
   ──► หน้าจอเด็ก · มุมผู้ดูแล · บันทึกสรุป (ไม่มีเสียงดิบ)
```
เกมอ่านค่าผ่าน `signalSource()` เท่านั้น สลับจากโหมดสาธิตไปอุปกรณ์จริงได้ที่ **มุมผู้ดูแล → แหล่งสัญญาณ** ในด่านเรียกเพื่อน
โดยไม่ต้องแก้ตรรกะเกม

## ช่องเสียง
- ไมค์บน (เหนือแผ่นกั้น ใต้จมูก) = ช่องจมูก, ไมค์ล่าง (หน้าปาก) = ช่องปาก
- INMP441 สองตัวใช้บัส I2S เดียวกันได้ โดยตั้งขา L/R ให้ต่างกัน ข้อเสนอตามต้นแบบ: จมูก = ซ้าย (L/R ต่อ GND), ปาก = ขวา (L/R ต่อ VDD)
  **ต้องยืนยันกับบอร์ดจริง** (เคาะไมค์ทีละตัวแล้วดูว่าค่าช่องไหนขยับ) และบันทึกเวอร์ชันแผ่นกั้น เกน ย่านกรอง และขนาดหน้าต่างที่ใช้

## หนึ่งข้อความ = หนึ่งหน้าต่างเวลา (แนะนำ 20–50 ms, ส่ง 20–50 ครั้งต่อวินาที)
JSON (WebSocket text frame):
```json
{"nasalPercent": 31.5, "speechDetected": true, "nasalDb": -30.2, "oralDb": -22.0, "clip": false}
```
หรือ CSV: `31.5,1,-30.2,-22.0,0` (สองช่องแรกบังคับ ที่เหลือไม่บังคับ)

| ช่อง | บังคับ | ความหมาย |
|---|---|---|
| `nasalPercent` | ใช่ | 100 × A_จมูก / (A_จมูก + A_ปาก) โดย A = ค่า RMS ของแต่ละช่องในหน้าต่างเดียวกัน หลังผ่านย่านกรองเดียวกัน |
| `speechDetected` | ใช่ | อุปกรณ์ตัดสินว่ามีเสียงพูด (เช่น ระดับรวมสูงกว่าเสียงรบกวนพื้นที่วัดตอนเงียบ และมี hangover สั้น ๆ) |
| `nasalDb`, `oralDb` | ไม่ | 20·log10(RMS / full scale) เป็น dBFS ของแต่ละช่อง · ช่องที่เป็นศูนย์ดิจิทัลให้ส่ง `null` (JSON) หรือ `-inf` (CSV) · ต้องส่งเป็นคู่ |
| `clip` | ไม่ | มีตัวอย่างเสียงแตะ full scale ในหน้าต่างนี้ (`true`/`false` หรือ `1`/`0`) |

## เว็บทำอะไรกับข้อมูล (ค่าตั้งต้นของต้นแบบ — ต้องวัดใหม่กับแผ่นกั้นจริง)
| สถานการณ์ | เงื่อนไข | ผลในเกม |
|---|---|---|
| ข้อมูลค้าง | ไม่มีข้อความใหม่เกิน 300 ms | หยุดนับ ช่วงพูดที่ค้างอยู่ถูกบันทึกเป็น “สัญญาณหลุด” ไม่ใช่ความผิดของเด็ก |
| หลุดการเชื่อมต่อ | WebSocket ปิด | ล้างค่าล่าสุดทิ้งทันที แล้วต่อใหม่เอง (รอ 1, 2, 4 แล้วทุก 5 วินาที; ระหว่างรอสถานะ “หลุด”) เมื่อเชื่อมใหม่ต้องได้ข้อความใหม่และต้องเงียบก่อน จึงเริ่มฟังอีกครั้ง |
| ช่องไมค์หาย | ช่องใดช่องหนึ่ง ≤ −96 dBFS หรือ `null` | เฟรมใช้ไม่ได้ (สถานะ `channel`) — ไม่ส่งค่า 0% / 100% ไปให้เกม · มุมผู้ดูแลบอกให้ตรวจสาย I2S/ขา L/R |
| สัญญาณล้น | `clip` หรือระดับ ≥ −1 dBFS ใน ≥ 20% ของช่วงพูด | ครั้งนั้น “ใช้ไม่ได้: ล้น” · เด็กเห็น “ลองเรียกด้วยเสียงสบาย ๆ อีกครั้ง” |
| เสียงเบาเกินไป | ช่วงพูดที่ดังที่สุดยังต่ำกว่า −45 dBFS | ครั้งนั้น “ใช้ไม่ได้: เบาไป” · เด็กเห็น “ลองเรียกด้วยเสียงปกติอีกครั้ง” (ไม่บอกให้ตะโกน) |
| ไม่มีช่องระดับเสียง | อุปกรณ์ส่งแค่สองช่องหลัก | ตรวจได้แค่หลุด/ค้าง · ด่านเรียกเพื่อนตอบสนองจากการตรวจพบเสียงอย่างเดียว · มุมผู้ดูแลแจ้งว่าตรวจเบา/ล้น/ช่องหายไม่ได้ |

ค่าเกณฑ์อยู่ที่ `QUALITY_DEFAULTS` (`src/signal/quality.ts`), `CALL_DEFAULTS` (`src/logic/call.ts`), `PROCESSOR_DEFAULTS` และ `SEGMENTER_DEFAULTS`

## เฟิร์มแวร์ต้นแบบคำนวณอย่างไร (`firmware/pakkeng_esp32/nasal_dsp.h`)
- 16 kHz ช่องละ 24 บิต หน้าต่าง 25 ms (ส่ง 40 ข้อความต่อวินาที)
- `nasalPercent` ใช้ RMS หลังตัวกรองย่านความถี่ตัวเดียวกันทั้งสองช่อง (ศูนย์กลาง 500 Hz กว้าง 300 Hz)
- `nasalDb`/`oralDb` เป็นระดับทั้งย่านหลังตัด DC — ช่องที่อ่านได้ 0 ล้วน (ขา SD เปิด pull-down) ส่ง `null`
- `clip` = มีตัวอย่างถึง 99.9% ของ full scale · `speechDetected` = ระดับในย่านกรองสูงกว่าเสียงรบกวนที่เรียนรู้เอง
  (+10 dB เริ่ม, +6 dB ต่อ, ไม่ต่ำกว่า −75 dBFS, hangover 150 ms) · หน้าต่างที่ได้ 0 ล้วนหรือไมค์หายไม่นับเป็นเสียงพูดและไม่ใช้เรียนรู้ห้อง ·
  เสียงดังต่อเนื่องเกิน 8 วินาทีถูกเรียนรู้เป็นเสียงรบกวน
- ต่อ WebSocket ไม่ติดภายใน 4 วินาที เว็บยกเลิกแล้วลองใหม่ตามรอบรอข้างบน

## การเชื่อมต่อ
- หน้าเว็บที่เปิดผ่าน https (เช่น Vercel) ต่อ `ws://` ไม่ได้ (mixed content) → ใช้ `wss://` หรือเปิดเว็บจากเครื่องในวง Wi-Fi เดียวกัน: `npm run dev -- --host` แล้วเปิด `http://<ip เครื่อง>:5173`
- ค่าเริ่มต้นในช่องที่อยู่: `ws://192.168.4.1:81` = เฟิร์มแวร์ในโหมด Wi-Fi ของบอร์ดเอง (`PakKeng-XXXX`) — ถ้าตั้งให้เข้า
  Wi-Fi บ้าน ให้ใช้ IP ที่ขึ้นใน Serial Monitor แทน · เปลี่ยนได้ในมุมผู้ดูแล

## ก่อนรายงานว่าใช้กับอุปกรณ์จริงได้
1. ส่งเสียงทดสอบเข้าไมค์ทีละตัว ยืนยัน mapping จมูก/ปาก
2. วัดเสียงรั่วข้ามแผ่น และวางแผ่นซ้ำหลายครั้ง (references/evidence-th.md: Wang 2026, de Boer & Bressmann 2014)
3. วัดระดับเงียบจริง แล้วตั้ง `deadDb`, `quietDb` ใหม่จากข้อมูล
4. วัดเวลาจากเสียงถึงหน้าจอบนมือถือเป้าหมาย (ยังไม่มีการวัด)
